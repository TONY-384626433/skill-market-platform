# 评委问答手册 —— 50 个预判问题及应答策略

> 准备越充分, 越不紧张。每个队员应能回答自己负责领域的问题。

## 一、关于项目定位与价值 (10 题)

### Q1: "这和直接用 Dify 的市场有什么区别?"

**应答策略**: 强调私域、安全、银行适配
**参考答案**:
"Dify 市场是面向全球开发者的通用市场, 技能质量和安全性无法保证, 也无法对接银行内部的 Zabbix、CMDB 等系统。我们的私域市场专为九江银行设计 —— 技能经过自动化安全审核、对接内网系统、全链路审计、符合监管要求。这是公域市场永远做不到的。"

### Q2: "为什么不用现成的开源方案, 比如 MCP Registry?"

**应答策略**: 承认开源价值, 但指出不足
**参考答案**:
"MCP Registry 是很好的协议层方案, 但它只解决了'技能如何被调用'的问题, 没有解决'技能如何被发现、管理、治理'的问题。我们的平台是基于 MCP 协议但不限于 MCP —— 还包括审核流水线、权限管控、运营激励、审计追溯等企业级治理能力。"

### Q3: "你觉得最核心的竞争力是什么?"

**参考答案**:
"安全内建。我们不是先做功能再做安全, 而是从第一天就把七层安全防护嵌入到每一次技能调用的全链路中。这在银行场景下不是可选项, 是必选项。"

### Q4: "这个项目的商业价值在哪里?"

**参考答案**:
"降本增效: 技能复用节省 200+ 人天/年。安全合规: 满足监管对 AI 应用的审计要求。知识沉淀: 防止员工离职带走 AI 经验。这三个价值直接对应银行的三大诉求。"

### Q5: "你如何说服其他团队把他们的技能放到你的平台上?"

**参考答案**:
"激励机制: 积分、徽章、排行榜、绩效关联。降低门槛: 三步入驻, 自动化审核, 零摩擦。展示价值: 优秀技能获得全行曝光, 开发者在技术大会上获得认可。"

### Q6: "2 个月的比赛时间, 能做出什么程度?"

**参考答案**:
"完整的 MVP —— 技能注册/搜索/安装/调用的全闭环, 4 个种子技能, 管理后台 + 审计日志。我们采用 Go + React 全栈开发, 前后端并行, 进度可控。"

### Q7: "如果九江银行未来不用 Dify 了怎么办?"

**参考答案**:
"我们的平台是协议层抽象 —— 技能通过 MCP 标准协议接入, 与具体的 AI 引擎解耦。即使未来 AI 引擎从 Dify 切换到其他平台, 技能只需修改适配器, 市场平台本身不受影响。"

### Q8: "你如何确保技能质量?"

**参考答案**:
"三道防线: 1) 自动化审核流水线 (格式/安全/功能), 2) 用户评分 + 评价体系, 3) 平台定期质量巡检。综合评分低于 3 分的技能会被标记并通知开发者整改。"

## 二、关于技术实现 (10 题)

### Q9: "技能调用的性能如何保证? 网关会不会成为瓶颈?"

**参考答案**:
"网关采用 Go 语言实现, 单机可支撑 10,000+ QPS。代理转发模式意味着网关本身不处理业务逻辑, 延迟增加 < 5ms。水平扩展只需加节点。"

### Q10: "敏感信息检测的准确率如何?"

**参考答案**:
"正则匹配层: 身份证/手机号/银行卡号 99%+ 准确率。语义识别层: 基于 LLM 的上下文推理, 解决非结构化姓名/地址的漏报问题。两阶段结合, 综合召回率 95%+, 精确率 90%+。"

### Q11: "你怎么处理 LLM 幻觉?"

**参考答案**:
"两个层面: 1) 技能设计层面 —— 对于确定性场景 (巡检、脱敏), 采用规则引擎 + LLM 混合架构, 关键数据不依赖 LLM 生成。2) 平台层面 —— 在技能审核流水线中进行幻觉测试, 对输出不稳定技能标记 risk flag。"

### Q12: "数据库选型为什么是 PostgreSQL 而不是 MySQL?"

**参考答案**:
"三个原因: 1) JSONB 类型天然支持技能 Manifest 的灵活存储和索引, 2) pg_trgm 扩展提供开箱即用的模糊搜索能力, 3) 九江银行 DBA 团队对 PG 已有运维经验。"

### Q13: "你们用 Go 还是 Python? 为什么混用?"

**参考答案**:
"Go 负责高并发的 API 网关和 CRUD 服务, 编译型语言性能好、部署简单。Python 负责 AI 生态对接 —— MCP Server、LLM 调用、数据处理, Python 生态在 AI 领域无可替代。各取所长。"

### Q14: "微服务之间如何通信?"

**参考答案**:
"同步: REST/gRPC。异步: RabbitMQ (审核事件、统计上报、审计日志批量写入)。服务发现: Kubernetes DNS。不引入过度复杂的服务网格。"

### Q15: "为什么不用 gRPC 而用 REST?"

**参考答案**:
"技能调用网关内部确实可以用 gRPC 优化延迟, 但我们对外暴露的技能端点优先采用 MCP 协议 (JSON-RPC 2.0), 因为 MCP 已经是 AI 工具的标准协议, Dify 和主流 Agent 框架原生支持。技术上不锁定厂商。"

### Q16: "可观测性怎么做?"

**参考答案**:
"三层: Metrics → Prometheus + Grafana (QPS/延迟/错误率), Logging → ELK (审计日志/应用日志), Tracing → 通过 Trace-ID 串联全链路调用。告警对接 Zabbix。"

### Q17: "如何处理大模型调用的 Token 消耗?"

**参考答案**:
"1) 技能层面: 要求开发者在 Manifest 中声明预估 Token 消耗。2) 网关层面: 监控每个用户/技能的 Token 用量并设置预算上限。3) 运营层面: 月度 Token 报表推动优化。"

### Q18: "前端为什么选 React 而不是 Vue?"

**参考答案**:
"九江银行内部 React 生态更成熟, Ant Design 5 的 React 版本功能最全面。技术栈选择优先考虑团队能力和行内兼容性。"

## 三、关于安全与合规 (10 题)

### Q19: "银行场景下如何保证数据安全?"

**参考答案**:
"五层: 网络层 (内网 + 防火墙), 传输层 (TLS 1.3), 应用层 (七层安全网关), 数据层 (敏感信息自动脱敏 + Vault 加密存储), 审计层 (全量日志, 保留 6 个月以上)。每层独立, 纵深防御。"

### Q20: "如何防止 API Token 泄露?"

**参考答案**:
"1) Token 只显示一次, 数据库中存 SHA256 哈希, 2) 支持 IP 白名单绑定, 3) 可设置过期时间和用量上限, 4) 异常调用模式自动告警和吊销, 5) 定期轮换提醒。"

### Q21: "监管审计时你能提供什么?"

**参考答案**:
"完整的审计轨迹: 谁(用户 ID)、什么时候(时间戳)、用什么技能、访问了什么数据(数据访问记录)、结果是什么、有没有涉及敏感信息。导出格式支持 CSV/JSON/PDF, 满足监管报送要求。"

### Q22: "如何处理不同密级的数据访问?"

**参考答案**:
"技能在 Manifest 中声明所需数据的密级 (L1-L4)。L3 及以上需要额外审批。网关运行时根据技能声明裁剪返回数据, 超出权限的部分自动过滤。这就是'最小权限'原则的落地。"

### Q23: "如果监管要求下架某个技能怎么办?"

**参考答案**:
"管理员后台一键下架, 技能状态变为 'archived'。所有已安装实例的 API Token 自动吊销。已记录的审计日志保留不变。整个过程可追溯: 谁下架的、什么时候、什么原因。"

## 四、关于落地与推广 (10 题)

### Q24: "推广的时候最大的阻力是什么? 怎么解决?"

**参考答案**:
"最大阻力是习惯 —— 大家习惯了各自为战。解决办法: 1) 管理层支持, 纳入技术规范, 2) 种子用户先行 —— 先让 3-5 个团队深度使用并看到价值, 3) 激励机制 —— 内部 Hackathon, 上架最多/评分最高的团队有奖。"

### Q25: "如果没人愿意贡献技能怎么办?"

**参考答案**:
"冷启动分三步: 1) 平台团队自己先贡献 10 个高质量种子技能, 2) 联合信息科技部评选'月度最佳技能', 给予实质奖励, 3) 将技能贡献纳入技术创新绩效考核, 和组织目标挂钩。"

### Q26: "如何衡量这个项目的成功?"

**参考答案**:
"定量: 技能数量 50+, 复用率 40%+, 月活 100+, 安全事件 0。定性: 团队开始主动问'这个在市场上有没有', 而不是'我们自己写一个'。文化转变比数字更重要。"

### Q27: "上线后你预计多久能看到效果?"

**参考答案**:
"3 个月: 种子技能被广泛使用, 第一批外部贡献者出现。6 个月: 技能数量自增长, 团队自发推荐同事使用。12 个月: 成为行内 AI 开发的标准入口。"

### Q28: "如果只能选一个指标来衡量成功, 你选什么?"

**参考答案**:
"技能复用率 —— 新项目中使用已有技能的比例。这个指标直接反映了平台的核心价值: 减少重复建设。从 0% 到 40%, 就是从'手工作坊'到'工业化'的转变。"

### Q29: "你考虑过国际化吗? 比如推广到其他城商行?"

**参考答案**:
"近期聚焦九江银行, 打磨产品。远期可以作为城商行联盟的共享平台 —— 每家银行的 AI 能力在脱敏后可以跨行共享, 形成行业级的 AI 技能生态。但那是明年的目标。"

## 五、关于团队与协作 (5 题)

### Q30: "你们的团队优势是什么?"

**参考答案**:
"跨学科互补: 计算机同学负责技术实现, 金融同学负责银行场景理解, 数据科学同学负责 AI 算法。加上九江银行信息科技部同事的业务指导, 确保方案不脱离实际。"

### Q31: "和九江银行员工怎么协作?"

**参考答案**:
"银行同事作为业务顾问: 提供真实场景需求、评审技能描述规范、对接内网系统 API、确保合规要求被满足。他们是'让方案接地气'的关键。"

### Q32: "如果队员中途退出怎么办?"

**参考答案**:
"我们有文档先行原则 —— 每个模块的架构设计、API 规范、代码注释都必须完善, bus factor 不能是 1。每个核心模块至少两人了解。"

## 六、压轴难题 (8 题)

### Q33: "如果 LLM 技术明年又有重大突破, 你的平台怎么办?"

**参考答案**:
"我们的平台设计就是协议抽象、引擎无关的。MCP 协议本身就是 Anthropic 为推动厂商中立而推出的。无论 LLM 怎么变, 技能的接入方式不变, 市场的治理逻辑不变。这就是平台的价值。"

### Q34: "你们的方案最大的风险是什么?"

**参考答案**:
"推广风险 —— 技术做得再好, 如果没有人用就是失败的。所以我们花了很大精力设计激励机制和冷启动策略。我们正视这个风险, 也准备了相应的应对方案。"

### Q35: "你觉得最大的竞争对手是谁?"

**参考答案**:
"不是 Dify 市场, 不是其他技术方案 —— 而是惯性。人们习惯了自己从头造轮子、把代码放在自己电脑里。打破这个惯性, 让团队愿意分享和复用, 这是我们真正要战胜的。"

### Q36: "如果你有更多时间和资源, 你会做什么?"

**参考答案**:
"三个方向: 1) AI Agent 自动编排 —— 根据任务自动组合多个技能。2) 跨行技能共享 —— 脱敏后的技能在城商行联盟内流动。3) 监管合规自动化 —— 让技能市场成为监管报送的数据源。"

### Q37: "一句话总结你的项目?"

**参考答案**:
"让 AI 能力从'个人电脑里的散落文件'变成'组织的公共基础设施'。"

### Q38: "如果我是九江银行 CIO, 给我一个理由批准这个项目?"

**参考答案**:
"这个项目解决了您最担心的三个问题: AI 安全不可控 —— 全链路审计解决了; AI 投资回报不明 —— 复用率数据量化了; 员工 AI 技能流失 —— 知识平台沉淀了。而且 2 个月就能看到 MVP。"

### Q39: "你们的平台和 AI Agent 是什么关系?"

**参考答案**:
"技能市场是 Agent 的武器库。Agent 需要工具才能做事 —— 市场里上架的每一个技能, 都可以作为 Agent 的一个 Tool。我们的平台让 Agent 开发者不用重复造工具, 直接在市场里挑选即可。"

### Q40: "十年后这个平台会是什么样的?"

**参考答案**:
"理想状态下, 平台本身会变得'透明' —— 就像水电一样, 你不会意识到它的存在, 但你需要任何 AI 能力时, 它就在那里。技能会上万, 用户会上千, 技能之间的自动编排和优化会成为标配。但治理逻辑 —— 安全、审计、合规 —— 这个底层不会变, 因为银行永远需要。"

## 七、应答万能公式

```
评委问题 → 
  1. 先复述问题 (确认你理解正确)
  2. 直接回答核心 (1-2 句话)
  3. 展开解释 (1-2 句话)
  4. 回到项目价值 (1 句话收尾)

示例:
Q: "和 Dify 市场有什么区别?"
A: "您的意思是我们的平台和 Dify 自带的工具市场有什么本质区别, 对吧。"
   "核心区别是三个: 私域、安全、银行适配。"
   "Dify 市场是公域通用市场, 无法对接银行内网系统, 也无法满足合规审计要求。
    我们的平台专门为九江银行设计, 七层安全防护, 全链路审计, 对接行内基础设施。"
   "本质上, Dify 市场是工具商店, 我们是 AI 治理平台。"
```

## 八、如果答不上来怎么办

1. **不要说"我不知道"** → 说"这是一个很好的问题, 让我从 XXX 角度来回答"
2. **不要编造** → 说"这个细节我们还在探索中, 目前的想法是 XXX, 下一步计划是 XXX"
3. **不要争论** → 说"您的观点很有启发性, 我们的设计是基于 XXX 考虑, 后续会认真评估您提到的方向"
4. **不要抢答** → 让最了解那个领域的人回答, 不要全一个人说
